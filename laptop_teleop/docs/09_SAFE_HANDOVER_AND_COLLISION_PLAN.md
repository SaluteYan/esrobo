# 遥操作安全接管与低延迟碰撞保护方案（设计稿）

本文针对“人体抬臂标定后，机器人从零位跟随时靠近躯干；开启实时碰撞检查又容易故障停机、降低跟随速度”的问题。**以下是拟实施方案，不代表当前代码已具备这些保护，也没有经过真机验证。** 当前代码路径和计算细节见 [08_CODE_AND_COMPUTATION.md](08_CODE_AND_COMPUTATION.md)。

## 1. 先区分目标冲突与碰撞检查故障

当前 `segment_direction_relative` 会将标定时的人体**上臂方向**对齐机器人 `q₀` 的上臂方向；保持标定姿态时，上臂目标原则上仍是机器人起始方向。但 `elbow_angle_mapping=direct_absolute` 将**当前人体肘弯曲角**作为目标几何弯曲角。用户已观察到启动时肘/大臂位移较短，而腕/小臂位移较大，前臂或灵巧手可能扫向中间躯干。这与代码路径一致：当肘近似固定、小臂长度为 `L_f`、前臂方向变化 `Δθ` 时，仅腕点的几何位移就是 `2L_f·sin(Δθ/2)`；例如 `L_f=0.25 m`、`Δθ=60°` 时为 `0.25 m`。`0.22 m/s` 会把目标位移分摊到更多周期，**不会主动生成绕开躯干的路线**。当前 [分区 IK](../../teleoperation/src/esrobo_teleop/ik/solver.py)只拟合肘/腕位置和关节限位，不优化躯干间隙；上臂对齐后的弯曲平面、手腕末端关节和标定后的人体动作也可能改变实际路径。尚无这次测试的关节/碰撞日志，不能确定最终接触配对或具体哪段路径先越界。

当前配置 `torso_collision_enabled=true`，但 `teleop_torso_collision_enabled=false`：启动、单侧回零有躯干几何检查，实时跟随没有逐周期几何检查。真实 `DualBackend.supports_prepare=False`，因为尚无双臂互碰扫掠检查；现有单侧 `TorsoCollisionGuard` 也不检查两臂互碰。[当前配置](../../teleoperation/config/teleop_config.yaml) · [双臂网关](../../robot_link/esrobo_link/backends.py)

把实时检查直接打开也不是完整解法。[`CommandTrajectory.propose()`](../../teleoperation/src/esrobo_teleop/robot/command_trajectory.py)先认证反馈到上一命令的未完成运动，再为每个候选认证覆盖反馈、上一命令、下一候选和估算制动点的整个关节区间盒；候选可以逐次缩小，但旧命令已不安全或连制动盒也无法认证时必须报故障。[`TorsoCollisionGuard`](../../teleoperation/src/esrobo_teleop/robot/torso_collision.py)使用手臂外包盒、躯干凸包和可选手指包络，区间盒可能比实际各轴同步轨迹保守；每次认证最多细分 64 个盒。若一次控制周期进行多次认证，50 Hz 控制循环会承受大量几何距离计算；超过反馈新鲜度预算还会引出独立的过期故障。几何拒绝、认证预算耗尽与计算超时必须在日志里分开看。

## 2. 第一步：不动硬件，复现并分类

保存一次曾开启实时检查的网关 `trajectory_fault` 事件及相邻反馈、命令、PICO 帧，至少提取：

| 字段 | 目的 |
| --- | --- |
| `collision_stage`、`pair`、`clearance_m`、`required_m` | 区分反馈到上一命令不安全、候选/制动盒不安全，确定接近躯干的是哪一段连杆；检查 URDF/安装间隙或手指包络是否过保守。 |
| `checked_lower_physical_rad`、`checked_upper_physical_rad`、`feedback_physical_rad`、`target_physical_rad` | 离线重放被拒绝的区间，比较起点、终点与盒内混合关节组合。 |
| `feedback_dt_s`、周期耗时、`swept path could not be certified within budget` | 区分几何不安全、64 盒预算拒绝和计算导致的反馈过期。 |
| PICO 标定/当前骨段方向、IK 肘腕目标、J1–J7 解 | 区分启动 `direct_absolute` 肘角偏置、弯曲平面翻转和操作员后续动作。 |

仓库当前没有找到可供复盘的本次真机日志；以下设计不能替代这一步的实测定位。**不要通过缩小安全间隙、忽略 `TrajectoryFault` 或只降低 `0.22 m/s` 来消除告警**：这些做法不能证明目标或尚未完成的控制器运动安全。

## 3. 第二步：把“从零位到接管姿态”从实时跟随中分离

建议引入 `CHECKING_ENTRY`、`APPROACHING`、`WAITING_FOR_ACTIVE_TARGET` 三个明确阶段，之后才进入 `ACTIVE`：

1. `CALIBRATING` 继续采人体参考，但将**标定参考**与**允许机器人开始跟随的接管姿态**分开。机器人保持失能/保持起点；让操作员保持一个双臂向外、前臂不横跨躯干的稳定姿态。
2. 对冻结的人体帧生成**未经过逐帧 `0.22 m/s` 限速的完整映射目标**，求机器人目标关节 `q_handover`。同时检查该目标姿态的单臂躯干间隙和（双臂时）臂间间隙；不可达或目标本身碰撞时提示重新摆姿态，不使能自动跟随。只检查目前的小首帧 `q_first≈q₀` 不足以证明最终方向目标安全。
3. 为用户观察到的“小臂先大幅扫过躯干”增设**安全外展中间姿态** `q_clear`：先从 `q₀` 移动肩/大臂，使肘、前臂和灵巧手整体获得足够躯干间隙；此时暂不追求人体的 `direct_absolute` 肘弯曲，可保持或限制 J4/J5–J7。再从 `q_clear` 引入目标肘弯曲，到达 `q_handover`。`q_clear` 不能只由“J1/J2 先动、J4 后动”的固定规则推断安全，必须检查整条 `q₀→q_clear→q_handover` 路径和各路点之间的异步关节扫掠；若几何上无安全路径，应拒绝该接管姿态。
4. 对两段路径做**一次非实时**受检规划。现有 [`ReturnPlanner.plan(start, goal)`](../../teleoperation/src/esrobo_teleop/robot/return_planner.py)可复用作单侧七轴路径搜索内核；当前 [`safe_return()`](../../teleoperation/src/esrobo_teleop/robot/nero_driver.py)执行器却只实现回零，需新增“去安全外展/接管姿态”的慢速、逐路点反馈复核执行器。双臂需要新的联合 14 轴/互碰检查与规划，不能把两个单臂七轴结果简单并排执行。
5. 执行前和每个路点重新确认人体姿态/反馈新鲜、控制器状态及实测到下一路点的扫掠区间；人体改变或检查失败就停在可认证的保持状态，要求重新选接管姿态。到达后检查反馈与目标误差，再发送新鲜的 `ACTIVE` 目标。
6. 将“重设**实际命令/IK 起点**”与“重算**人体到机器人方向对齐**”拆成两个接口。当前 `Pipeline.initialize(measured)` 会同时重算 `R_align` 和目标历史；若规划到 `q_handover` 后照旧调用，保持不动的人体姿态可能被重新映射成另一个目标，形成第二次跳变。接管时应固定已选定的映射关系，仅用到位后的实测反馈重置限速器、IK 种子和轨迹状态；或者显式定义一套经过验证的新接管参考，并保证切换前后的完整目标连续。

**大臂方向是否改为绝对映射。** 如果目标是机器人上臂在统一机器人基坐标中与人体上臂方向一致，那么最终跟随目标确实应使用经过坐标系校准的绝对方向；当前相对模式只保证人体相对标定姿态的转动传到机器人，保持标定姿态时上臂仍指向机器人会话初始方向。现成的 `segment_direction_absolute` 直接跳过标定上臂到机器人零位的 `R_align`，并同时跳过 `_neutral_relative_forearm()` 与近直臂弯曲平面稳定分支；它会让抬臂标定姿态对应一个可能远离机器人零位的完整上臂/前臂目标，不能通过直接修改 YAML 解决启动碰撞。应先验证 PICO 腰部相对坐标经 `source_to_robot_rotation` 和符号变换后确实对应机器人基坐标，再计算该绝对目标、检查可达和碰撞，按上述受检路径从零位接管。若只想调整大臂方向而保留当前前臂稳定逻辑，需要拆分两段的映射模式，并验证模式切换时目标连续。绝对方向目标也只在关节可达、两臂和躯干间隙允许的范围内追踪。

这是**先检查并规划一个静态接管路径，再实时跟随**。若机器人零位与目标姿态之间确实必须绕躯干，单纯线性放慢也不能解决碰撞。作为临时实验，可在进入接管前使用“人体相对标定肘角变化映射到机器人零位弯曲”的 `relative` 肘模式，使人体保持标定姿态时更接近 `q₀`；它会牺牲当前要求的绝对人体肘弯曲一致性，切回 `direct_absolute` 之前仍需上述受检路径，不能作为最终替代。

## 4. 第三步：保留跟随响应，提前减速而非边界才报错

实时阶段需要一个**已证明保守**、计算时间有上界的安全域。可先围绕受检接管路径与任务工作区，用现有精确守卫在非实时阶段认证有限的关节区间盒；运行时只对“反馈、上一命令、下一候选、估算制动点”构成的盒做快速包含判断。处于认证域内部时走现有反馈约束轨迹；靠近边界时根据剩余间隙和可达制动距离逐步降低目标速度或转为安全保持，而不是等候选和制动都不可认证时才硬故障。超出认证域、模型不确定、反馈过期或制动路径无法认证，仍须拒绝新的运动命令并按现有故障策略处理。

若认证盒过窄而影响任务，再设计轻量的保守连杆胶囊/躯干包络距离检测，并离线与现有 URDF 守卫对照，确保它不会把精确守卫拒绝的状态放行。不能只检查肘/腕两点：前臂、手掌和异步 `MOVE_J` 轴运动都可能进入躯干。双臂还需在**同一机器人状态**中检查左臂、右臂与互碰；两个独立单臂检查相加不等于双臂安全。可参考 [MoveIt Servo 官方文档](https://moveit.picknik.ai/main/doc/examples/realtime_servo/realtime_servo_tutorial.html)中“接近碰撞时缩放速度”的控制原则，但该文档不等于本项目已有对应实现或安全证明。

此处最关键的是**提前制动**：安全余量应覆盖测量/传输时延、尚未完成的上一 `MOVE_J` 命令、最大允许制动距离和模型误差。只在 `q_next` 与躯干距离小于阈值时把新命令改为 `hold`，可能已经来不及停止上一命令。现有 `CommandTrajectory` 对反馈—命令—候选—估算制动盒的检查必须保留同等或更强语义。

## 5. 代码落点与验收顺序

| 位置 | 拟改动 |
| --- | --- |
| [`body_device.py`](../../teleoperation/src/esrobo_teleop/device/body_device.py)、[`pipeline.py`](../src/esrobo_laptop/pipeline.py) | 暴露未限速的完整方向目标；分离人体标定、映射对齐与当前实测命令起点；给接管阶段提供稳定性/目标诊断。 |
| [`solver.py`](../../teleoperation/src/esrobo_teleop/ik/solver.py) | 对冻结接管姿态求完整目标；先拒绝碰撞或不可达解，不靠逐帧限速掩盖终点风险。必要时再加入安全域内的近似目标投影。 |
| [`gateway.py`](../../robot_link/esrobo_link/gateway.py)、[`backends.py`](../../robot_link/esrobo_link/backends.py) | 增加接管状态和明确的“新 ACTIVE 目标已收到”门禁；将规划/执行与正常跟随串行，保持目标租约、停止与反馈约束。 |
| [`return_planner.py`](../../teleoperation/src/esrobo_teleop/robot/return_planner.py)、[`nero_driver.py`](../../teleoperation/src/esrobo_teleop/robot/nero_driver.py) | 复用单侧受检规划内核，增加非零目标执行；新增有限计算量的运行时安全域查询/提前减速，保留失败时的故障处理。 |
| [`torso_collision.py`](../../teleoperation/src/esrobo_teleop/robot/torso_collision.py) | 离线认证与记录最小间隙/配对；双臂时另实现联合互碰模型，不沿用“另一侧固定零位”的单侧假设。 |

验收按顺序进行：**静态模型核对 → 相同 PICO 录制输入的离线重放 → 含两臂躯干/互碰的仿真 → 单侧低速真机验证 → 具备联合检查与停止能力后的双臂真机**。记录碰撞配对和最小间隙、规划成功/拒绝原因、接管前后目标连续性、每周期计算时间分布（尤其 p95/p99 和超过 `20 ms`、`100 ms` 的次数）、输入到反馈方向滞后，以及停手/反向时的超调。模拟通过不代表真机几何与时延通过；真实双臂自动准备在当前代码中仍被禁止。
